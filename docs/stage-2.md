Статус: проект для утверждения, 13.09.2026. Результат — этот документ и `docs/openapi.yaml` версии контракта 1.0.0. Реализации, миграций и плана следующего этапа нет. Утверждённый `docs/stage-1.md` и его R0 не изменяются. **Q01–Q09 — утверждённые дополнения заказчика**, а не новые положения первоначального BUSINESS; ниже ссылки B относятся к правилам вместе с явно отмеченными в этапе 1 уточнениями.

## 1. Границы и решения

### Проекты и зависимости

Стрелка означает ссылку проекта: `Motiva.Application → Motiva.Domain`; `Motiva.Infrastructure → Motiva.Application, Motiva.Domain`; `Motiva.Api → Motiva.Application, Motiva.Infrastructure`; `Motiva.Worker → Motiva.Application, Motiva.Infrastructure`. Domain ни на один другой проект не ссылается. Api и Worker не ссылаются друг на друга. Дополнительного Contracts нет: внешние DTO принадлежат Application, HTTP-заголовки и Problem Details — Api.

| Проект | Ответственность и внутренняя группировка | Запрещённая зависимость/обязанность |
|---|---|---|
| Motiva.Domain | Чистые правила в EmployeeAccess, Campaigns, Progress, Economy, Achievements, Competitions: аудитория, календарные интервалы, переходы, пакет, точные суммы, ранги. Типизированные решения с B-ID. | EF, HTTP, Npgsql, Valkey, S3, чтение текущего пользователя или часов из глобального состояния. |
| Motiva.Application | Сценарии тех же функциональных групп плюс Exports/Audit. Входная валидация, текущие права, порядок транзакционного сценария, вызовы правил Domain, DTO и порты хранения. Одна точка входа сценария для HTTP, bootstrap и функциональных тестов. | Реализации инфраструктуры, DbContext/DbSet/IQueryable, обход validation/authorization из «удобного» тестового helper. |
| Motiva.Infrastructure | EF Core/Npgsql mappings, транзакции и блокировки PostgreSQL, запросы с явным tenant scope, Valkey cache, S3, durable jobs, поток CSV. Одна БД и один контекст на единицу работы; не отдельный контекст на каждый модуль. | Самостоятельное назначение прав, новый бизнес-исход вместо решения Application/Domain, возврат IQueryable/EF entities наружу. |
| Motiva.Api | JWT middleware, REST-маршруты, привязка DTO, HTTP-версии/ETag, Problem Details, отмена запросов. `Program`/выделенная папка Composition — сборка DI и конфигурации Infrastructure. | Endpoint не вызывает Infrastructure, DbContext, Npgsql или S3 SDK напрямую; не меняет время через HTTP. |
| Motiva.Worker | Запуск application-сценариев фиксации итогов, снимка/файла и очистки. Composition — отдельная сборка DI без выпуска JWT. | Worker orchestration не исполняет SQL/SDK напрямую и не реализует экономические правила заново. |

| Выбор | Причина | Цена/ограничение |
|---|---|---|
| Модули одной системы, общая PostgreSQL-транзакция вместо независимых сервисов учёта | B17/B19/B20 требуют одновременного результата в нескольких предметных областях. Не нужны распределённые компенсации для обычного начисления. | Общая БД — граница доступности и миграций; внутренние модули не развёртываются независимо. |
| Синхронное выполнение прогресса/денег; PostgreSQL jobs только для рейтингов и выписок | Клиент сразу получает окончательное решение награды, включая отказ; тяжёлый файл и S3 не удерживают транзакцию учёта. | Время записи включает блокировки; очередь не скрывает перегрузку основной БД. |
| Пессимистические блокировки средств + уникальные ограничения, а не Valkey-lock | Работает между двумя Api и после рестарта; вся проверка пакета находится рядом с его записью. | Конкуренция за один кошелёк/бюджет сериализуется; порядок прихода наград не обещан. |
| Сохранённые строки снимка выписки вместо одного timestamp-фильтра | Поздний commit и повтор после падения не меняют CSV. | Дополнительное дисковое место и запись до 100 000 строк снимка; чтение/файл затем потоковые. |
| Короткий общий барьер прав на компанию | Один проверяемый порядок изменения профиля, владельца, тегов, grants и нового обращения. | Изменение настройки кратко ждёт текущие обращения компании; допустимость под нагрузкой проверяется, не объявляется без измерения. |

### Абстракции и конкретные проблемы

| Граница Application | Что скрывает и зачем нужна |
|---|---|
| Транзакционный исполнитель `IUnitOfWork` | Общая транзакция, таймауты, порядок получения блокировок, commit и неоднозначный исход при разрыве соединения. Не создаёт вложенных независимых транзакций. |
| Предметные хранилища Access/Campaign/Progress/Economy/Competition/Export/Audit | Операции по конкретному сценарию: загрузить текущие разрешения, заблокировать набор остатков, сохранить пакет, прочитать DTO-страницу. Нет универсального `Repository<T>` или отдельного интерфейса на каждую таблицу. Используют одну единицу работы. |
| `IBusinessClock` с асинхронным получением момента | Все Api/Worker используют часы PostgreSQL (`clock_timestamp()`), прочитанные внутри нужной транзакции **после барьера**; часы разных процессов не расходятся на закрытии соревнования. Календарные правила получают зафиксированный момент через TimeProvider. Тестовый адаптер использует управляемый TimeProvider; production HTTP для управления им отсутствует. |
| `ICatalogCache` / `ILeaderboardCache` | Только разрешённые неперсональные снимки, проверка возраста и bounded fallback. Не универсальный cache-aside для любых данных. |
| `IExportObjectStore` | Поток загрузки/проверки/чтения/удаления, multipart и подпись ссылки без знания SDK в Application. |
| `IBackgroundJobs` | Атомарно поставить задание с изменением состояния, захватить с lease и fencing token; повтор после падения любого Worker. |

Ни отдельный mediator, ни шина сообщений, ни generic CRUD, ни event sourcing не требуются. Неизменяемый журнал движений служит проверке остатков; состояние прогресса и настройки не восстанавливаются воспроизведением всех событий при каждом запросе.

Суммарные счётчики/порог в API и хранении — checked Int64; переполнение представления или установленного T05 предела — 400 с полным rollback. Авторитетное представление точных моментов в БД — bigint UTC ticks по 100 нс, включая границы и сортировку; не округлять пользовательскую границу до PostgreSQL timestamp. Непредставимое значение — 400. Микросекундные часы PostgreSQL представимы точно. |

## 2. Модель данных

Условные имена — проект таблиц, не миграция. Во всех предметных таблицах есть `company_id NOT NULL`. `PK(id)` ниже означает `PK(company_id,id)`; любой FK на предметный объект включает компанию и при необходимости родителя. UUID не является разрешением. Для masterId используются составные FK `(company_id,master_id)`. Денормализованные `campaign_id/stream_id` связаны составными FK с соответствующим родителем, а не произвольными копиями.

Для удаления черновых Stream/Task/Milestone/Challenge также используется tombstone с сохранением идентификаторов/аудита. Ссылки и уже занятые коды не очищаются архивом. При публикации проверяется весь актуальный граф, включая ресурсы, периодичность, вехи, интервалы и владельца; бюджет может быть нулём. Изменение дочерней настройки сериализовано с публикацией и повышает также агрегатную version кампании, чтобы конкурентная публикация со старой версией получила 412.

### Учёт: бюджеты, кошелёк, операции

| Сущность | Ключи и ограничения | Назначение |
|---|---|---|
| Wallet | PK; UQ `(company,masterId)`; FK Employee. Профиль + кошелёк создаются одной транзакцией. | Ровно один кошелёк, владелец неизменяем; ни удаления, ни перевода. |

Нет общей казны и прямого присваивания остатка. |

Nullable-поля строго определены видом; полного чужого кошелька в DTO операции нет. | Immutable результат, включая экономический отказ. TaskReward связан с Completion/Event, не принимает отдельный клиентский номер. Оригинал отмены читается обычным SELECT; синхронизация — advisory-ключ Reversal(companyId, originalOperationId), §3. |
| OperationAmount | PK `(company,operation,resource)`; positive amount; ресурсы пакета не повторяются. | Предписанные суммы, в том числе при отказе; **не движения**. Для отмены — точные позиции оригинала. |
| WalletMovement | PK `(company,operation,resource)`; FK Operation/WalletBalance; ненулевой signed amount; masterId/campaign/original/time неизменяемы. | Только Posted начисление/трата/отмена. Это источник выписки и объяснения кошелька. Выделение бюджета не создаёт строку кошелька. |
| BudgetMovement | PK `(company,operation,campaign,resource)`; FK Budget; ненулевой signed amount. | Allocation +, Credit −, CreditReversal +; Spend/SpendReversal отсутствуют. |
| BusinessRequest | UQ `(company,actor,kind,exact_number)`; canonical request bytes, hash, result ID и замороженный HTTP DTO/status/Location в каноническом формате `/api/v1/...` (§5). | Бессрочная защита B24, атомарна с Operation. Event использует свою область B16. Нет отдельного commit «номер занят» до результата; replay возвращает исходный сохранённый Location. |
| IdempotentRequest | UQ `(company,actor,operation,target,key)`; canonical request, hash, неизменяемый успешный ответ с Location `/api/v1/...` и expiresAt не раньше commit+24h. | Прочие создающие POST; replay возвращает исходный сохранённый Location. Очистка после минимального срока допустима; экономические номера в этой очистке не участвуют. |

Одна успешно проведённая отмена защищена частичным индексом `UNIQUE(company_id, original_operation_id) WHERE kind='Reversal' AND status='Posted'`. Exclusive transaction-level advisory lock `Reversal(companyId, originalOperationId)` даёт согласованный путь всех попыток, а индекс остаётся окончательной защитой успешного слота. Declined его не занимает. Отмена отмены/выделения бюджета не допускается входным сценарием.

Operation, OperationAmount, защищённые движения и принятые события не получают UPDATE/DELETE из application-роли БД; миграционная роль отделена. Оригинальная Operation и её OperationAmount читаются обычным SELECT, без `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE` или `FOR KEY SHARE`: все эти locking clauses требуют UPDATE-привилегии, согласно [PostgreSQL 17 SELECT](https://www.postgresql.org/docs/17/sql-select.html). Для advisory-синхронизации UPDATE на Operation не нужен. Если EXECUTE ограничивается, application-роли разрешён вызов используемых `pg_catalog.pg_advisory_xact_lock(integer, integer)` и `pg_catalog.pg_advisory_xact_lock_shared(integer, integer)`. Эта роль не владелец таблиц, не superuser и не наследует привилегированную роль; IsReversed и SECURITY DEFINER не используются. Для существующих изменяемых проекций/состояний заданий права UPDATE сохраняются.

История и контрольные суммы остатков записываются одной транзакцией. База обеспечивает FK/unique/check, а соответствие суммы многопозиционного пакета между журналами — единый сценарий Economy под блокировками; один CHECK не объявляется защитой межтабличного инварианта. Сверка по журналу в persistence/E2E проверяет эту границу. Внешние номера хранятся `bytea`: T05 допускает ASCII, а не только печатные символы; PostgreSQL text не подходит для NUL. Канонические запросы/замороженные ответы с такими строками также хранятся байтами, не jsonb.

| Событие учёта | Бюджет A | Кошелёк A | Прогресс/очки/достижения/счёт |
|---|---:|---:|---|
| Выделение 10 | +10 | 0 | Не меняет |
| Пакет задания с A=10 | −10 | +10 | Изменяются завершением независимо от выдачи ресурсов |
| Ручная награда 10 | −10 | +10 | Не меняет |
| Трата 7 | 0 | −7 | Не меняет |
| Полная отмена начисления 10 | +10 исходной кампании | −10 | Не отзывает |
| Полная отмена траты 7 | 0 | +7 | Не меняет |
| Declined / NotPlanned | 0 | 0 | Declined/NotPlanned задания сохраняет принятое выполнение |

### Прогресс, рейтинг и выписки

## 3. Транзакционные протоколы

### Текущие права и версии

1. Api проверяет JWT; из него получают company/actor/masterId/role. User должен иметь текущий активный профиль в своей компании; service использует текущие grants. Все проверки выполняются также при вызове Application из теста/доверенного bootstrap с явно выданным контекстом. Bootstrap имеет только отдельное полномочие первичного создания компании/администратора.
2. В PostgreSQL transaction-level advisory **shared** lock на компанию удерживается обычным обращением до фиксации решения/получения ответа из БД. Любое изменение активности, тегов, владельца, grants, принимаемых ресурсов и настроек берёт **exclusive** lock того же ключа. Проверка актуального состояния — новым statement **после** получения lock, в Read Committed. Не использовать старый snapshot, созданный до ожидания. Коллизия хеша lock key допустима лишь как лишнее ожидание, не как пропуск проверки company/FK.
3. Если отзыв уже committed, новое обращение увидит его; если операция первой получила shared lock, она целиком завершается перед отзывом. Ответ HTTP может физически дойти позднее, но новый запрос не использует прежние права. Личный профиль берётся из JWT, подмена request masterId не меняет исполнителя. При заблокированном получателе повтор отмены разрешён только Admin — **доп. Q03**.
4. Изменяемая настройка имеет strong ETag `"vN"`. После проверки доступа отсутствие If-Match даёт 428, несовпадение — 412; UPDATE проверяет version и повышает её с аудитом. PATCH поддерживает только явно перечисленные поля, массив заменяется целиком. Правила публикации проверяются на актуальном графе. Для POST дочерних настроек используется Idempotency-Key и сериализация с публикацией; If-Match для создания T04 не требует.
5. Детальное GET настройки с ETag всегда читает согласованные тело и версию из PostgreSQL. Нельзя выдать старое тело кеша с новой ETag. Экономическая операция не защищается If-Match кошелька; DELETE export защищён блокировкой/состоянием, без ETag.

Основа механизма — [transaction-level advisory locks и блокировки строк PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html). Барьер прав — выбранное применение этих механизмов, а не готовая гарантия библиотеки.

### Повторы и единый порядок блокировок

| Шаг | Действие |
|---|---|
| 1 | Барьер компании; текущая аутентификация/авторизация и tenant scope объекта. Для повтора проверяются как запрошенная область, так и область сохранённого результата: существование номера не раскрывает чужой payload. Для новых кредитов/трат и их повторов проверяется активность получателя; для отмен — Q03. |
| 2 | Транзакционный lock ключа дедупликации. B16 scope `(company,source,eventNumber)` без task/season; B24 `(company,actor,kind,operationNumber)`; остальные POST — T05 scope. SQL UNIQUE остаётся окончательным ограничением. Ожидание ограничено, по исчерпанию 503 + Retry-After. |
| 3 | При занятом номере сравнить канонические существенные поля (включая основание/причину). Перестановка JSON-полей, ресурсных позиций и наборов тегов не меняет смысл; порядок/регистр внешнего номера не нормализуется. Hash — ускорение, сравниваются и канонические байты. Совпадение возвращает исходные 201/ID/DTO/Location, расхождение 409. После текущих прав не проверять заново архив/время/аудиторию/деньги. Исключение удалённой выписки — ниже. |
| 4 | Для нового запроса — структурная/семантическая валидация и проверка принадлежности. Неверные/неизвестные поля, отсутствующие/чужие объекты, недопустимый вид отмены, отсутствие прав, блокировка и overflow не занимают номер. Корректная операция может дать сохранённый Declined по **доп. Q08**. |
| 5 | Далее порядок: shared барьер стрима для нового progress event; **exclusive transaction-level advisory lock Reversal(companyId, originalOperationId)** для новой отмены, затем отдельный statement READ COMMITTED проверяет успешную предыдущую Reversal (§3 ниже); строка Wallet получателя (сериализует также его прогресс/очки/достижения); строки Budget по возрастающему resourceId. CreditReversal берёт исходные Budget, SpendReversal их не берёт. Выделение берёт только соответствующий Budget. Ни один сценарий не берёт Wallet после Budget. Прогресс нового периода создаётся под Wallet lock. |
| 6 | Сформировать изменения Domain; проверить все остатки/лимиты до проводок; сохранить согласованный результат, журнал и неизменяемый ответ. В самом конце получить HistoryClock компании и присвоить history_seq; после него не брать иные предметные блокировки и не обращаться к сети. Commit фиксирует всё. |
| 7 | После commit отправить ответ. При потере соединения на commit клиент может получить 503/обрыв, но не вымышленный Declined. Повтор **того же** номера на любом Api ищет сохранённый результат; если commit отсутствовал, номер свободен. Результат не хранится только в памяти/Valkey. |

Предварительная форма JSON должна быть читаемой даже для поиска повтора; бессмысленный JSON не превращается в успешный replay. Для существующего корректного результата mutable-предусловия не перезапускаются. Для временного HTTP Idempotency-Key успешный ответ хранится ≥24 h с момента commit, не продлевая бизнес-срок ссылки. Неуспешная транзакция не оставляет «вечный InProgress»; занятость — lock текущей транзакции. На истечение технического ключа клиент не должен рассчитывать как на бессрочную дедупликацию.

### Advisory-ключ отмены и свежая проверка (D201)

Все Api используют одно стабильное кодирование логического ключа. Для company/dedup/stream и нового reversal-пространства применяется двухаргументная форма `(integer, integer)`: первый аргумент — фиксированное пространство, второй — детерминированный хеш составляющих. Пространство не хешируется вместе с данными и не может случайно превратиться в другой тип замка; одноаргументная форма bigint здесь не смешивается с двухаргументной.

| Пространство / первый аргумент | Составляющие логического ключа по порядку | Режим |
|---|---|---|
| Company = 1 | companyId | Существующий shared/exclusive барьер компании |
| Dedup = 2 | Для B16: `B16, companyId, sourceActorId, eventNumber`; для B24: `B24, companyId, actorId, kind, operationNumber`; для T05: `T05, companyId, actorId, operation, target, key` | Существующий exclusive lock дедупликации, области прежние |
| Stream = 3 | companyId, streamId | Существующий shared admission / exclusive finalization barrier |
| Reversal = 4 | **companyId, originalOperationId** | Exclusive для CreditReversal и SpendReversal |

Каждая составляющая кодируется как 4-байтная беззнаковая длина в big-endian и следующие за ней UTF-8-байты; перед последовательностью так же кодируется метка `motiva-lock-v1`. UUID имеют канонический lower-case D-формат; kind/operation/scope — фиксированные идентификаторы, target — канонический целевой ресурс существующей области. Внешние номера/key сохраняются побайтно, без нормализации. Второй аргумент — первые 4 байта SHA-256 этой последовательности, прочитанные как unsigned big-endian `u` и приведённые к signed Int32: `u`, если `u < 2^31`, иначе `u − 2^32`. GetHashCode и зависимое от процесса/платформы представление UUID не используются. Для отмены вызов — `pg_catalog.pg_advisory_xact_lock(4, hash32)`; initiator, новый operationNumber и Api-процесс **не входят** в этот ключ.

Коллизия внутри Reversal только дополнительно сериализует разные оригиналы; tenant scope, FK и сравнение исходного ID остаются обязательными. Разные первые аргументы исключают пересечение Reversal с company/stream/dedup locks и сохраняют общий порядок. Блокировка транзакционная: освобождается при commit/rollback; ожидание входит в существующий общий ограниченный deadline, по исчерпанию — 503/Retry-After без отдельного commit номера. Session-level замки, новые таблицы блокировок, внешние зависимости, Valkey-lock и process-local semaphore не добавляются. Семантика функций описана в [PostgreSQL 17 advisory lock functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).

| Порядок новой отмены | Проверка и результат |
|---|---|
| Company barrier → текущая авторизация → business dedup lock → replay/конфликт | Исходная Operation и позиции доступны обычным SELECT для tenant scope/прав/валидации. Совпавший номер возвращает исходные ID/201/DTO/Location; изменённые существенные данные — 409. До этого остаются текущие права и Q03; найденный replay не ждёт advisory-ключ отмены и не переигрывает решение. |
| Reversal advisory lock → **новый отдельный SQL statement READ COMMITTED** | Только после завершения ожидания проверить наличие `kind='Reversal' AND status='Posted'` для той же company и originalOperationId. Не использовать проверку до ожидания, старый snapshot или объединённый statement, в котором snapshot был получен до advisory lock. Так проигравшая попытка видит commit победителя. |
| Решение по оригиналу → необходимые Wallet → Budget | Уже успешная Reversal даёт новое **201 Declined/AlreadyReversed**, а не 409; известный непроведённый допустимый оригинал — 201 Declined/OriginalNotPosted. Эти отказы не требуют блокировки средств. Иначе под Wallet и, только для CreditReversal, исходными Budget по возрастающему resourceId выполнить прежние проверки достаточности и пределов. Недостаток одной позиции пакета — сохранённый Declined/InsufficientBalance без любых обратных движений. |
| HistoryClock в самом конце → commit | Новая Operation отмены, её OperationAmount, проведённые движения при Posted, BusinessRequest с исходным ответом/каноническим Location и history_seq — одна транзакция. Исходная Operation, суммы и прежние движения не обновляются. После HistoryClock нет новых предметных блокировок или внешнего I/O. |

**Доп. Q08 сохраняется:** разные номера одного оригинала используют общий Reversal lock, но создают собственные неизменяемые результаты. Declined не занимает успешный слот: после штатного изменения условий новая попытка с новым номером допустима; replay старого Declined остаётся прежним Declined даже после чужой успешной отмены. Отсутствие прав, неизвестный оригинал и техническая неудача без согласованного результата номер не занимают. При заблокированном получателе и новая отмена, и replay разрешены только Admin по **доп. Q03**.

### Прогресс и деньги

| Сценарий | Атомарное действие |
|---|---|
| Новое событие | После shared барьера стрима зафиксировать acceptedAt из общей временной основы; проверить Published/неархивность, активность, обе аудитории и `[start,end)`. Рассчитать пересечение периода с кампанией, `credited=min(goal,old+delta)-old`. Переполнение проверяется в расширенном промежуточном типе, а не через переполнение Int32. |
| Первое завершение | Под Wallet lock: Completion; прибавить заданные points StreamPoints; найти **все** пересечённые вехи; вставить AchievementAward с UNIQUE сезона; обновить каждый ChallengeScore, чей интервал содержит acceptedAt. Ресурсная награда пустая → NotPlanned, иначе одно решение на весь пакет. |
| Непустой пакет | Сначала доступность **его** ресурсов по **доп. Q02**. Архив любой позиции → весь Declined/ResourceUnavailable. Только затем проверка всех заблокированных Budget; недостаток любого → весь Declined/InsufficientBudget. В успехе одинаковые суммы одновременно Budget−/Wallet+. Никаких независимых commit по ресурсу. |
| Событие после цели | Новый event сохраняется с credited=0, без повторного Completion/points/reward. Участник подходящего челленджа всё равно появляется со score=0. Это отличается от повтора прежнего event ID. |
| ManualCredit | Одно разрешённое средство из бюджета; по **доп. Q01** Published сейчас `[start,end)`, текущая аудитория кампании и активный получатель; предыдущие выполнения/аудитория задания не требуются. Не меняет Completion/points/achievement/score. Недостаток/архив/срок/аудитория дают окончательный business Declined при корректном правомочном поручении. |
| Allocation | Admin; выбранный ресурс; Draft/Published до конца срока и сезона, включая будущее и до начала — **доп. Q09**. Увеличивает только Budget. Невозможные состояние/время либо архив ресурса дают сохранённый отказ. Ни уменьшения, ни переноса, ни отмены Allocation нет. |
| Spend | User только свой Wallet либо service с текущим grant выбранной системы/ресурса. Система принимает ресурс, получатель активен; Budget не читается/не увеличивается. Недостаток — окончательный Declined. |
| CreditReversal | Текущие права на исходную кампанию, при блокировке только Admin. Общий Reversal advisory lock → свежая проверка успешной отмены → Wallet → исходные Budget по возрастающему resourceId. Оригинал/позиции читаются обычным SELECT. Проверить все балансы и верхние границы восстановления; один успешный reversal slot. Все Wallet−/Budget+ либо сохранённый отказ без движения. Архив/прошлый сезон не препятствуют. |
| SpendReversal | Admin или service, представляющий **ту же зарегистрированную систему покупок**, с текущим grant ресурса. Равенство первоначального service subject не требуется: полномочие дано системе; сотрудником инициированная её покупка тоже относится к ней. Тот же Reversal advisory lock и свежая проверка успешной отмены, затем Wallet; **Budget не блокируется и не меняется**. Полностью Wallet+ при Posted. Q03 при блокировке; исходная Operation неизменяема. |

Успешное начисление, отказ награды и NotPlanned не смешиваются. Возвращение средств отдельной отменой не изменяет первоначальный ответ, прогресс, очки, достижения или ранг. Обычные операции под PostgreSQL Read Committed безопасны здесь благодаря явным блокировкам всех читаемых изменяемых предусловий; уровень изоляции сам по себе не объявляется решением.

## 5. REST-контракт

Машиночитаемый источник методов, схем, статусов и прав — `docs/openapi.yaml`, OpenAPI 3.1.0. Все перечисленные ниже маршруты имеют префикс **`/api/v1`**: в YAML он указан в `servers`, а ключи `paths` остаются без него. Заголовок **Location всегда содержит путь от корня хоста `/api/v1/...`** к конкретному созданному ресурсу, включая сохранённый Declined. Placeholders соответствуют GET-маршруту и подставляются значениями ID созданного результата; у createReversal это ID **новой** Operation отмены, не originalOperationId из POST URL. BusinessRequest/IdempotentRequest сохраняют этот канонический Location вместе с исходным ответом; replay возвращает его без изменения. Location не является S3 download URL: у createDownloadLink он указывает на ресурс ссылки в API, а подписанный URL находится в `DownloadLinkDto.url`.

Например, `POST http://localhost:8080/api/v1/employees` с `Location: /api/v1/employees/123` разрешается в `http://localhost:8080/api/v1/employees/123`. Префикс не добавляется к `paths` повторно. JWT — единственная аутентификация; login/registration/token endpoints отсутствуют. Версия URI v1 и `info.version=1.0.0`; после утверждения любое изменение регистрируется поправкой к контракту. D201/D202 — поправка к этой сдаче без изменения состава API, схем и утверждённых HTTP-исходов. Структура выбрана по [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0.html), не генерацией из ещё не существующего кода.

| Чтение, изменение существующей настройки | GET/PATCH 200 JSON; у настройки strong ETag. PATCH с отсутствующим полем оставляет его прежним, null только там, где разрешён схемой. |
| Удаление | 204 без тела. Повтор DELETE export 204; для изменяемых настроек текущий доступ + If-Match, удалённая настройка 404. |
| Неверный JWT / нет полномочий | 401 / 403, включая повтор после отзыва. Не раскрывать объект чужой компании или недоступный личный объект — 404. Неактивный собственный профиль — 403. |
| Неверные поля/неизвестный ресурс/не та система/неподдержанный вид отмены | 400 для полей/бизнес-валидности известной ссылки, 404 для отсутствующего/чужого объекта. Номер не занят. Неподходящий scope прав — 403. |
| Повторный номер с другим смыслом, дубликат кода, недопустимый переход | 409 с NumberConflict/IdempotencyConflict/CodeConflict/StateConflict. **Известный непроведённый** допустимый оригинал отмены — сохранённый Declined/OriginalNotPosted, а не этот 409. |
| Нет/старая версия | 428 PreconditionRequired / 412 PreconditionFailed; слабая ETag, wildcard и неверный формат — 400. |
| БД/конкурентное ожидание временно недоступны | 503 TemporarilyUnavailable + Retry-After; повтор того же номера/key. Никакой сохранённый успех/отказ не подделывается. |
| Неподготовленный/удалённый файл | 409 ExportNotReady / ExportDeleted; проверка requester/current rights раньше. |

Каждая ошибка — `application/problem+json`: type/title/status/detail/instance/code/traceId/errors (типизированный массив field/code/message, обычно пустой). `application/json` не меняет схему из-за роли, пустого массива, попадания в кеш или состояния выписки. Имена/описания, коды, теги, интервалы и числовые ограничения точно заданы в OpenAPI; целые Int64 нельзя преобразовывать через неточное IEEE-754 double; дополнительные неизвестные поля отклоняются.

Окончательные причины бизнес-отказа Operation: InsufficientBudget, InsufficientBalance, ResourceUnavailable, CampaignUnavailable, RecipientOutsideAudience, OriginalNotPosted, AlreadyReversed. Общего нового приоритета этих причин не вводится: **доп. Q02** задаёт приоритет ResourceUnavailable перед InsufficientBudget только для пакета задания. Ошибки полномочий/валидации не превращаются в Declined.

### Пагинация и свежесть

| Вид чтения | Порядок/фильтры и устойчивость |
|---|---|
| Все обычные коллекции | Только `{items,nextCursor}`; default limit=50, max=100. Пустая коллекция `items=[]`, `nextCursor=null`. Opaque HMAC cursor содержит версию формата, company, reader, маршрут/scope/канонические фильтры, верхнюю границу и последний ключ. Текущие права проверяются заново на каждой странице. Точный набор применимых фильтров указан в YAML. |
| Append-only операции, движения, события, аудит, выдачи достижений | Возрастающий `(history_seq,id[,resourceId])`. В конце каждой записывающей транзакции блокируется HistoryClock компании, назначаются последовательные seq, lock держится до commit. До этого шага все предметные изменения готовы; после — только финальные вставки/commit. Обычная sequence с номером до commit **не подходит**. |
| Первая страница истории | Один согласованный read statement/snapshot получает committed upperSeq и строки `seq<=upperSeq`; продолжения сохраняют upperSeq. Транзакция с более ранним createdAt, но поздним commit получит новый seq и не вклинится внутрь этого обхода. Пропусков/дублей ранее существовавших строк от вставок нет; новая первая страница их увидит. |
| Настройки, ExportRequest, изменяемые Task/Stream results | По неизменяемому `(created_seq,id)` либо ключу `(periodStart,taskId,masterId)`/`(season,streamId,masterId)` результата, с границей создания первого запроса. Значения могут обновляться между страницами; это не неизменяемая выписка. Удаление/потеря прав может скрыть запись. Для created_seq применяется тот же порядок commit, что HistoryClock. |
| Фильтры | Operation/Movement/Event/Audit — `[from,to)` по времени записи (Event — acceptedAt); ресурс для операций/движений, компания из JWT. TaskResult — по началу фактического периода; StreamResult/AchievementAward — season; личные/кампанийные пути дополнительно campaign/stream/task/master там, где заданы в YAML. Все даты требуют offset. |
| Каталог | Неперсональный кеш payload; текущий доступ и отбор аудитории в PostgreSQL. Свежесть `asOf` передаётся заголовком **As-Of**, сохраняя общий envelope. Данные деталей с ETag из PostgreSQL; управление O/A не читает устаревшую настройку. |
| Рейтинг | Исключение T04: `{challengeId,state,asOf,items}` для top N (limit 50/100), отдельный `{challengeId,state,asOf,position}`; position=null при допустимом доступе и отсутствии строки. Две выдачи могут иметь разные asOf. Строка строго masterId/score/rank. Final не заменяется Live из кеша. |

## 6. Выписка: снимок, файл, публикация, удаление

| Переход | Механизм и граница фиксации |
|---|---|
| Создание → Pending | Проверить requester/scope, интервал/ресурс, Idempotency-Key; сохранить запрос и job одной транзакцией. Движения не копируются в момент заказа. |
| Pending/Error без снимка → Processing | Worker claim в отдельной короткой транзакции. Затем lock ExportRequest; если Deleted — закончить. **Один INSERT…SELECT со statement snapshot PostgreSQL** копирует только видимые committed WalletMovement `[from,to)`, выбранного scope/resource, вместе со всеми CSV-полями; в этой же транзакции сохраняются snapshotAt/rowCount и Processing. Нет последовательного перечитывания исходных движений порциями с разными snapshots. |
| Неудачный первый старт | Если snapshot-транзакция не committed, нет успешного начала/частичного состава; следующий старт может видеть новые движения. После успешного commit `snapshotAt` и набор строк никогда не пересоздаются при retry. Это принципиально отличается от отказа последующей загрузки в S3. |
| Processing/Error со снимком → новая попытка | Читает только ExportSnapshotRow. Persist attempt/generation/уникальный object key до внешнего I/O; затем читает строки порциями и пишет UTF-8 поток multipart, вычисляя SHA-256 и длину. API не загружает файл в память; worker держит ограниченный буфер, например 8 MiB. |
| Успешная загрузка → Ready | Проверить длину и SHA-256 **фактических байтов объекта** потоковым GET, а не лишь доверять метаданным upload. Lock ExportRequest; проверить generation/fence и отсутствие Deleted; записать неизменяемый object key/digest/rowCount и Ready одной транзакцией. После Ready этот key никогда не перезаписывается. |
| Crash между upload и Ready | Повтор claim видит durable ExportAttempt. Если объект существует, повторно проверяет его против детерминированных байтов того же снимка, затем публикует при актуальном fence; иначе создаёт новую попытку с другим key. Потерявший lease worker не публикует устаревший результат; его объект известен очистке. |
| Техническая ошибка | Публичный Error с безопасным errorCode; durable job повторяет после 1/5/30/60 s, далее с ограниченной паузой до восстановления. Snapshot остаётся. Нет API «заново посчитать состав» и нет произвольного конечного количества попыток, оставляющего незавершённый запрос навсегда. |
| Ready → DownloadLink | Текущие права requester; lock ExportRequest после lock Idempotency-Key. Проверить Deleted **до** возврата ранее сохранённой ссылки. Для нового key проверить Ready и подписать GET на 60 s, сохранить Link+неизменяемый успешный ответ одной транзакцией. Подпись локальная; основная транзакция не ждёт S3. |
| Повтор key ссылки | Возвращает исходный Link ID/URL/201/Location, даже если URL истёк; TTL не продлевается. Новый ключ создаёт новую ссылку. После Deleted — 409 ExportDeleted, независимо от сохранённого key. |
| Любое состояние → Deleted | Заказчик с текущими правами; lock ExportRequest; пометить Deleted, увеличить generation/fence, записать audit и cleanup job одной транзакцией. Повтор DELETE 204. Строка запроса и её история остаются. Уже выданный URL может работать до истечения своих ≤60 s. |
| Очистка | По durable перечню attempts удалить готовые/побочные объекты и abort multipart; повторно сверить prefix LIST и ListMultipartUploads. Последнее находит также upload, начатый до crash перед сохранением uploadId: его key уже записан в ExportAttempt. Внешние операции имеют deadline, старые Worker не начинают новые upload после утраты lease. Незавершённый upload может закончиться после первого прохода удаления: tombstone остаётся в повторной очистке до завершения/истечения всех attempts и контрольного LIST. Не полагаться только на одноразовый DELETE или eventual lifecycle S3. |
| Два Worker / восстановление | Jobs получают `FOR UPDATE SKIP LOCKED`, lease и монотонный fence. Состояние меняет лишь владелец текущего lease; истёкший lease захватывается повторно. Poll cleanup ≤30 s, I/O deadline ≤30 s, backoff ≤60 s; контроль полного удаления объекта/parts ≤10 min **после восстановления зависимостей** проверяется E2E. |

Основа состава — [MVCC snapshots PostgreSQL 17](https://www.postgresql.org/docs/17/transaction-iso.html); долговечность состава после завершения транзакции даёт выбранная материализация строк, а не сохранённое имя SQL snapshot. Нельзя держать открытую snapshot-транзакцию на всю загрузку в S3.

Точный различающий пример A36: заказ создан t0. До первого успешного формирования committed кредит +10 A (t1) и трата −7 A (t2). Транзакция L уже присвоила движению время t2, но ещё не committed. В t3 стартующий statement фиксирует только две видимые строки: `+10−7=3 A`. После t3 L commits +4 A, затем новая трата −1 A: живой Wallet `3+4−1=6 A`, **снимок по-прежнему две строки и 3 A**. Crash после upload не добавляет ни +4, ни −1. Отдельный сценарий: первая snapshot-транзакция откатилась — тогда успешный следующий старт может включить эти committed движения, потому что прежнего снимка ещё нет.

| Header | `operationId,masterId,resourceCode,amount,kind,campaignId,originalOperationId,createdAtUtc` |

## 7. Аутентификация, кеш и эксплуатационные пределы

| Тема | Решение и механизм |
|---|---|

Явное отображение role Employee/Admin, Owner отсутствует. Не принимать дубли/противоречия identity claims, неожиданный алгоритм, неподписанный/просроченный токен. Проверка по [ASP.NET Core JWT bearer](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/configure-jwt-bearer-authentication?view=aspnetcore-10.0). |

Секреты/токены/signed URLs не в Git/логах/отчётах. Начальные компании и активный Admin через доверенный Application bootstrap; остальное через обычные UC/защищённый API. Ротация/SSO/refresh не добавляются. |
| Немедленность | Business profile/owner/grants — PostgreSQL на каждое обращение, включая GET/replay/link, под §3. Роль Admin меняется новым JWT; мгновенный отзыв JWT вне объёма T03. Потеря Admin не делает пользователя заказчиком чужих выписок. |
| Каталог Valkey | Только неперсональный payload. Ключ включает company, scope/фильтры, версию формата. asOf ставится при получении DB snapshot, expiresAt=asOf+30 s. Список доступных человеку кампаний/заданий фильтруется по **свежим** состоянию и правам из PostgreSQL, не по кешированным тегам/статусу. |
| Рейтинг Valkey | Только score/masterId/rank и snapshot asOf; TTL до asOf+5 s. Проверка права читать и Final-state из PostgreSQL перед выдачей. Own position не берётся из чужой кеш-строки; вычисляется для masterId JWT с явно указанным asOf. |
| Старый/corrupt cache | Проверить company/schema/asOf/absolute expiry; invalid → miss. Late fill получает абсолютное истечение, не новый относительный TTL; атомарное сравнение asOf не позволяет более старому заполнению затереть новое. Valkey поддерживает [PEXPIREAT](https://valkey.io/commands/pexpireat/). Инвалидация после изменения — ускорение, безопасность от неё не зависит. |
| Отказ Valkey | Ожидание ≤30 ms, затем bounded PostgreSQL fallback; не кэшируются балансы, права, решения, прогресс-eligibility и business dedupe. In-process ограничитель повторных подключений допустим только для защиты зависимости, не для финансовых блокировок. |
| Отказ S3 | Учёт не обращается к S3; Export остаётся Pending/Processing/Error и retry. Link на уже существующий объект подписывается локально, фактическое скачивание при отказе S3 может временно не работать. Такое скачивание не делает экономическую операцию неуспешной. |
| Отказ PostgreSQL | Ограниченные pool/connect/lock/command deadlines и общий CancellationToken; 503, Retry-After=1 s для временного ожидания. После неясного commit клиент повторяет тот же номер. Нельзя вернуть якобы старые права/деньги из кеша. |
| Readiness/liveness | Readiness проверяет возможность основной работы с БД и применённость схемы, сбой →503. Valkey/S3 деградируют отдельные функции, не всю readiness основной системы. Liveness подтверждает работающий процесс и не вызывает restart loop лишь из-за внешнего отказа. |
| Наблюдаемость | trace/correlation ID в ответах/структурированных логах; latency/error/status/replay/conflict/decline по видам, DB lock waits/pool, cache miss/fallback, queue age/lease/retries, finalization delay, snapshot/export/cleanup duration, CPU/RAM. Поручения и grants изменяются с предметным аудитом, логи его не заменяют. |
| Ограниченная работа | Нет внешнего I/O в денежной транзакции. Целевой предел core transaction 2 s с отменой/rollback; DB statement/lock/idle limits и внешний deadline согласованы. Export snapshot имеет отдельный ограниченный бюджет, до 30 s; он не удерживает Wallet/Budget/HistoryClock на копировании строк. Генерация/GET S3 вне него. |

### D201: ожидаемые конкурентные трассы

Это **проект runtime-проверок последующих стадий, не выполненные тесты**. Бизнес-данные создаются штатными UC/HTTP; прямой SQL для проверки привилегий/ограничений остаётся только в отдельной persistence-группе T08. Ожидание проигрывающей попытки на advisory-ключе и последующий отдельный statement проверяются управляемыми барьерами двух соединений, без произвольного Sleep.

| Проверка | Условия/действия | Ожидаемый результат |
|---|---|---|
| D201-a — два Api, разные номера/инициаторы | Из Wallet 10 A проведена Spend 7: осталось 3.
